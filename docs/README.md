# 文档地图

> **营小商** —— 一个智能体，提示词管判断，工具管能力，skill 管判据，上下文由模型按需取。

## 1. 权威顺序

冲突时按这个顺序取，前者压后者：

1. [`principles/single-agent.md`](principles/single-agent.md) —— 设计原则，唯一权威。
2. [`mvp/mvp-v3.md`](mvp/mvp-v3.md) —— 这一轮交付什么、怎么验收。
3. [`requirements/`](requirements/README.md) —— 一个需求一份文档（R01–R20）+ 未立项池。
4. [`30-research/`](30-research/) —— 同类项目调研，只作参考。
5. `cases/`、`screenshots/` —— 案例与界面材料，不是口径。
6. [`90-archive/`](90-archive/) —— 历史文档，只读追溯，**不能用来反问当前实现**。

## 3. 怎么用

| 你要做的事 | 先看 |
|---|---|
| 判断一个功能该不该做、该放哪 | 原则 §2（提示词 / 工具 / skill）、§7（五问） |
| 写代码前确认行为 | 对应需求 §2 落位、§4 契约、§6 验收 |
| 加一个新能力 | 需求 §2；落不了位就进 `backlog.md` |
| 验收一轮对话 | MVP §3 场景 + 对应需求 §6 |
| 改文案 / 品牌 | R19 |
| 查历史为什么这么设计 | `90-archive/`，只读 |

## 4. 维护规则

- **一份需求一份文档**：不在一份里塞两个需求，也不在别人的文档里长出一节新功能。
- **需求不写实现分支**：需求文档只写「要什么」和「怎么验收」；代码路径只出现在第 7 节「现状与差距」。
- **改口径先改原则**：原则没改就改需求，视为跑偏；原则改了要逐个检查受影响的需求。
- **状态只有三种**：MVP / 后续 / 不做。后续与不做都要写触发条件。
- **不设第二套口径**：旧文档整体归档，不在原位保留「另一份也对」的版本。

## 5. 归档说明

`90-archive/00-mvp-v2/` 是 2026-10-25 拆分前的全部设计文档（原 `docs/00-mvp/`、`docs/10-long-term/`、`docs/20-features/`），
三个目录整体平移，内部相对链接仍然有效。其中仍然成立的结论已经拆进 `requirements/`；
归档只用于追溯，**不作为实现依据**。
