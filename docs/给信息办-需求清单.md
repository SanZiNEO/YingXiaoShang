# 营小商 · 校内服务器与小程序资源申请

> 用途：向学校信息化办公室申请**服务器资源、大模型 API 额度、小程序主体资质**。
> 提交时可自行补机构全称与联系人；本文件不含任何密钥、账号或学生真实数据。
> 版本：v2 · 2026-11-07（取代 v1「纯本地」口径）

---

## 〇、一页纸摘要

**项目是什么**：面向市场营销课程的教学 AI 助教。学生用手机或电脑打开即可：提问（回答引用教材原文）→ 出练习题 → 在线作答 → 交卷判分 → 查看学情。
老师可以在同一套系统里看到全班进度、哪道题错得多、谁需要单独辅导。

**我们申请什么**（三件，缺任何一件都无法进入正式教学）：

| # | 申请事项 | 为什么必须是学校的 |
|---|---|---|
| 1 | **校内服务器**（1 台虚拟机） | 学情数据必须集中存储，老师才能看到全班；40–60 人并发访问；必须 7×24 在线、有固定地址、有备份与日志 |
| 2 | **学校大模型 API 额度 / 统一网关** | 全班一学期调用量远超个人测试额度；个人额度有限速、有余额上限、无法开票、一旦用尽全班同时停摆 |
| 3 | **小程序主体资质**（理想目标） | 微信对**个人主体不开放教育类目**，个人身份无法上架教育类小程序 |

**保底目标**：校内服务器 + 网页版（学生用浏览器打开，手机电脑都能用）。
**理想目标**：在此基础上加微信小程序（学生打开微信点一下就能用，不需要安装任何东西）。

**我们不要的东西**：不要经费现金、不要工位、不要专门人力。只要**资源与技术配合**。

## 一、为什么必须用学校服务器（不是"想要"，是"做不到"）

这一节是本次申请的核心，请重点看第 1 条。

### 1. 学情数据必须集中，否则这个产品的一半价值不存在

教学价值的一半在**老师端**：谁没做、哪道题全班错、哪个学生掉队。
这些数据如果分散在每个学生的电脑上，老师永远看不到——**老师端在技术上就无法实现**。
只有数据集中到一台服务器，老师才能打开一个页面看到全班。

> 这一条不是"体验更好"，而是"本地模式下老师端等于不存在"。

### 2. 手机端无法在本地实现

学生用手机打开浏览器或微信小程序，手机上没有我们的程序，只能访问一个网址。
**网址必须指向一台 7×24 在线的服务器**。个人电脑关机、休眠、IP 变动，都做不到。

### 3. 并发与稳定性

一个班 40–60 人，在课堂或作业时段会集中访问。个人电脑无法承载并发，也没有带宽保障。

### 4. 合规要求（学校必须能审计）

- 网络日志留存不少于 6 个月（网络安全法要求）
- 学生数据的存储位置、访问记录、备份与删除，需要可查
- 出现问题时需要能定位到具体请求

个人电脑无法提供日志留存、备份与审计能力。

### 5. 统一更新与分发

现在每次更新都要给每个学生发一个 150MB 的压缩包，学生常遇到下载不全、被杀毒软件拦截。
部署在服务器上后，学生打开就是最新版，不需要安装任何东西。

### 6. 备份与容灾

学期中间服务器故障，如果数据在个人电脑上，无法恢复。集中部署才能做定期备份。

## 二、申请的服务器规格（可直接转给运维）

| 项目 | 需求 | 说明 |
|---|---|---|
| 形态 | 1 台 Linux 虚拟机（校内虚拟化平台即可） | 不需要物理机、不需要 GPU、不需要集群 |
| 操作系统 | Ubuntu 22.04 LTS（或学校标准镜像） | 我们提供 Docker 镜像，运维按标准流程部署 |
| CPU / 内存 | 起步 2 vCPU / 4 GB；若 60 人并发建议 4 vCPU / 8 GB | 无 GPU 需求 |
| 磁盘 | 100 GB SSD | 课程材料 + 新闻库 + 学情数据；一年增量约 10–20 GB |
| 网络 | **仅需开放 443（HTTPS）入站**；不需要开放数据库端口 | 数据库不对外暴露 |
| 地址 | 校内可解析的域名（或校内 IP + 域名） | 小程序场景**必须**是已备案的 HTTPS 域名，不能用 IP |
| 出站 | 放行模型服务域名（`api.deepseek.com` 或学校统一网关地址） | 这是最容易踩坑的一条，见第五节 |
| 备份 | 每周一次全量，保留 4 周（学校现有备份策略即可） | 数据量小，成本极低 |
| 数据库 | PostgreSQL（多用户并发）或沿用 SQLite（小规模） | 由运维按学校标准选；我们不挑 |
| 部署方式 | Docker 容器（单容器即可） | 便于运维审计与回滚 |

**不需要**：公网 IP（除非要做小程序/校外访问）、GPU、对象存储、负载均衡、Kubernetes。

### 如果要做到「理想目标：微信小程序」，服务器还需满足

1. **公网可访问 + 已备案域名 + HTTPS**（微信强制要求，不能是 IP、不能用自签证书）
2. 域名需在微信小程序后台配置为「服务器域名」
3. 小程序内容安全接口需要能访问微信的 `api.weixin.qq.com`

> 若学校只批校内服务器（无公网域名），我们可以做到「校内网页版」（保底目标），
> 小程序则需要额外批一个公网域名与备案。

## 三、为什么必须用学校的大模型 API 额度

### 1. 用量测算（一个班一学期）

| 项目 | 估算 |
|---|---|
| 班级规模 | 40 人 |
| 每人每学期对话轮次 | 约 200 轮（含查资料、出题、判分） |
| 每轮平均 token | 输入约 5,000 / 输出约 800 |
| **一个班一学期总量** | 输入约 4,000 万 token，输出约 640 万 token |
| **费用估算** | **约 300–800 元/学期/班**（按当前国内主流模型价格，含多轮工具调用取上限） |
| 两个班一学期 | 约 600–1,600 元 |

> 结论：**费用不高**（比一次等保测评低两个数量级），但**必须走学校账号**，
> 原因不在钱，在下面三条。

### 2. 个人额度为什么不能用（三条硬理由）

1. **限速与限额**：个人测试额度有并发与每日上限。40 人同时提问会直接触发限流，学生看到的是"太频繁，请稍后再试"，课堂直接停摆。
2. **不可持续与不可追溯**：额度用尽即全班报错；费用记在个人账上，无法开票、无法纳入教学经费、无法审计。
3. **合规**：教学系统调用第三方模型，应使用学校可控的账号或网关，便于记录、审计与追责。

### 3. 三种落地方式（请学校选一种，我们都能对接）

| 方式 | 说明 | 我们的工作量 |
|---|---|---|
| **A. 学校已有统一大模型网关** | 最理想。我们对接学校网关地址与鉴权 | 1–3 天适配 |
| **B. 学校申请一张专用 API 账号** | 学校管理账号与充值，我们只拿调用凭证 | 1 天 |
| **C. 学校采购模型服务并分配额度** | 按学校采购流程 | 依流程 |

> 无论哪种方式，**接口都保持 OpenAI 兼容格式**，后续更换厂商不需要改业务代码。

### 4. 用量控制（让学校放心）

我们会在系统里做三重限制，并且这些数字可以写进管理办法：

- 单学生每日轮次上限（可配置，例如 100 轮）
- 单次请求上下文上限（已在代码中限制）
- 班级总额度告警（达到 80% 通知管理员）
- 全部调用可按学生/班级统计（便于核算与教学研究）

## 四、为什么必须由学校主体申请微信小程序

> 说明：本项目**不做 App**，只需要微信小程序（学生打开微信点一下就能用，无需安装）。

### 1. 硬门槛：个人主体没有教育类目

微信开放平台的**个人主体不能选择教育类服务类目**。教育类目需要：
- 《事业单位法人证书》（学校主体），部分类目还需《办学许可证》
- 由学校人员担任小程序管理员
- 完成微信认证（300 元/年，学校现有认证主体通常可复用）

**这一条无法通过技术手段绕开**，是平台规则。

### 2. 小程序上线还需要

| 要求 | 说明 |
|---|---|
| 已备案域名 + HTTPS | 小程序只能请求已配置的 HTTPS 域名，不能用 IP |
| 服务器域名配置 | 在小程序后台把我们的接口域名加入白名单 |
| 内容安全接口 | 需调用微信内容安全检测（学生输入需过检），我们会实现 |
| 隐私协议 | 需在小程序内展示并取得同意（采集学号、姓名） |
| 教育类应用备案 | 小程序属于教育类移动应用，是否需在教育部平台备案，**请学校明确口径**（备案主体是学校） |

### 3. 我们能承担的部分

- 小程序前端开发、审核材料准备、隐私协议文案、内容安全对接
- 与学校现有账号体系（统一身份认证）对接，避免自建密码体系
- 上架后的日常维护与问题响应

### 4. 如果学校暂时不批小程序

保底方案是**校内网页版**：学生用手机浏览器打开一个校内网址，功能一致（除微信入口）。
代价是需要学生手动保存网址，且校外访问受限。

## 五、需要配合的配置项（不花钱，但会直接卡住上线）

| # | 事项 | 需要谁 | 为什么关键 |
|---|---|---|---|
| 1 | **出站放行模型服务域名** | 网络运维 | 校园网常限制第三方 API。被拦时学生只看到"连不上模型服务器" |

| 5 | **SSL 证书** | 运维 | 可用学校现有证书或免费证书，小程序必须有效 HTTPS |
| 6 | **数据库/服务器访问权限** | 运维 | 建议由运维统一纳管，我们只申请应用部署权限 |

## 九、项目现状（供评估可行性，不是"我们已经能自己跑"）

我们已完成**原型验证**，用来证明技术路线可行、不是空想：

- 完整教学闭环已在单机环境跑通：提问 → 引用教材原文 → 出题 → 作答 → 交卷判分 → 学情档案
- 40 余个课程知识点、教材原文、案例材料已结构化入库
- 14 组自动化测试，每次改动都跑，防止改坏
- 错误提示全部中文化（断网/额度/磁盘/启动失败都有具体指引）

**但原型不具备正式教学条件**，原因正是本次申请的三件事：

| 原型状态 | 正式教学要求 |
|---|---|
| 单机运行，数据各存各的 | 数据集中，老师可见全班 |
| 用个人测试额度，有限速、有上限 | 学校账号/网关，可审计可核算 |
| 只有桌面端，需逐个发安装包 | 手机/网页直接打开，无需安装 |
| 无日志留存、无统一备份 | 满足学校审计与备份要求 |

> 也就是说：**技术已验证，缺的是承载正式教学的基础设施。**
