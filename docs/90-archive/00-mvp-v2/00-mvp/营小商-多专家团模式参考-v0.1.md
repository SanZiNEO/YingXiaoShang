# 多专家团模式参考 · v0.1

> 这份文档只回答一件事：**WorkBuddy 的「专家团」是怎么组织多角色协作的，营小商现在为什么不用，将来真要做时照什么形状做。**
>
> 它不是实现依据，是参考。当前实现口径见 `营小商-MVP-v2.0.md`，现在只有一个 agent。

---

## 1. 官方把能力分了三层

| | 是什么 | 一句话 |
|---|---|---|
| **Skill** | 工具能力 | 让 AI 能做某件事 |
| **专家** | 能力 + 经验 | 单角色，独立人设、方法论、工具链 |
| **专家团** | 多位专家 + 协作流程 | 有团长、有分工、并行执行、整合交付 |

三层的区别不在提示词长短，在于**有没有协作流程**。专家团多出来的是：谁拆任务、谁干什么、结果怎么汇。

## 2. 一个专家团就是一个目录

```text
my-team/
├── .codebuddy-plugin/plugin.json   # expertType: "team"
│                                   # teamInfo: { leadAgent, memberAgents[] }
├── agents/
│   ├── trading-team-lead.md        # 团长（文件名必须带团队前缀）
│   ├── market-analyst.md           # 团员
│   └── ...                         # 一个角色一个文件
├── skills/                         # 可选，团队共享的技能
├── avatars/                        # 团队与每个成员的头像
└── settings.json
```

团长和团员**都是 markdown**，frontmatter 只有五个字段：

```yaml
name: market-analyst
description: Technical analyst - analyzes charts, indicators, and price patterns
displayName: { en: "Marco", zh: "Marco" }
profession:  { en: "Technical Analyst", zh: "技术分析师" }
maxTurns: 50        # 团长 200，团员 50
```

**值得学的一点**：角色是数据，不是代码。加一个角色 = 加一个 md + 在 `memberAgents` 里挂个名字，不动调度逻辑。

## 3. 调度：两个工具 + 一套禁令

工具只有两个，且**只有团长能用**：`AgentTool`（调其他 agent）、`SendMessage`（给成员发消息）。开发者不能自己加工具，权限由系统分配。

团长的提示词里写死了一段「团队协作机制」，核心是四条：

1. **建立团队**：任务开始时团长亲自建团队，**只能由团长建，不许委派**；
2. **调度成员**：按阶段下发独立任务，**团长不得代写成员的专业产出**；
3. **消息中转**：成员产出回传团长，由团长转给下一阶段，**跨成员信息必须经团长中转，不得直连**；
4. **成员结论为准**：专业产出必须先由对应成员输出，团长只做编排与汇编。

配了五条「严禁行为」，其中两条是关键：

> ❌ 禁止跳过「建立团队」，直接自己模拟成员发言或并行写出多角色内容
> ❌ 禁止自己代写任何团队成员的专业产出

这两条为什么重要：多角色系统最常见的失败不是「调度错」，而是**团长觉得派活太慢，自己把活干完了**。禁令把这条堵死了。

## 4. 运行时隔离

- **独立上下文**：每个成员加载相同的项目上下文（项目说明、MCP、技能），但**不继承团长的对话历史**，只收到团长写的任务说明。
- **共享任务列表**：所有成员可见、可认领、可改状态。
- **邮箱**：支持单发与广播（广播消耗随人数线性增长）。
- **进程内运行**：成员跑在同一个进程里，不额外起服务。
- **落盘**：团队配置、成员信箱、任务列表都写在本地目录。
- **粒度建议**：每个成员 5–6 个任务。太细，协调开销超过并行收益；太粗，返工风险高。

## 5. 营小商现在的选择：一个 agent

**原因不是「设计上只该有一个人」，而是 DSH 的多代理在实验目录里**（`packages/experimental/agent-team`，README 自己标注 experimental 且要求持久化会话存储）。MVP 不押实验特性。

所以现在的形态是：

```text
packages/agent/agents/mentor.md      1 份主提示词：身份、判断、回复规矩、边界
packages/agent/references/           7 份手册，模型用 load_reference 按需读
  teaching-playbook.md                 判断该追问还是该讲、讲到什么深度
  case-playbook.md                     怎么精讲案例与新闻
  question-playbook.md                 怎么出题与批改
  research-bp-playbook.md              怎么做调研设计与 BP
  competency-rubric.md                 四维能力、证据分级、成长卡
  counterexample-playbook.md           怎么找反例与失败模式
  artifact-schemas.md                  结构化产物长什么样
```

这就是「专家团」拆掉协作层之后剩下的东西：**一份总纲 + 一堆按需查的手册**。角色没有了，专业内容一点没丢。

之前那版是 6 份角色提示词（团长 + 5 个成员），代码里还有 `MEMBERS` 常量、`memberTool()`、按成员分的产物白名单。问题不在于多，在于：

1. **团长提示词要求 `TeamCreate`，但代码里没有这个工具**——模型被要求走一个走不通的流程，干脆自己干完；
2. 于是 5 个成员从没被调用过，`trace.members` 永远是空数组；
3. 角色白名单让「加一个能力」要同时改提示词、常量数组、产物白名单三处。

## 6. 将来真要做多 agent，照这个形状做

不要从「写 5 份角色提示词 + 一个调度工具」开始——那正是这一版踩过的坑。按 WorkBuddy 已经验证过的顺序：

| 顺序 | 要做的事 | 不做的后果 |
|---|---|---|
| 1 | 角色**文件化**：一个角色一个 md + 一张 manifest | 加角色要改代码 |
| 2 | 成员有**独立上下文**，不继承对话历史，只收任务说明 | 成员和团长重复读材料，token 翻倍 |
| 3 | 团长必须**先建团队再调度**，且建团队只能团长做 | 团长直接自己干完，成员永远不上场 |
| 4 | 写死**「禁止代写成员产出」** | 同上，而且产出质量退化成单 agent |
| 5 | **跨成员信息必须经团长中转**，禁止直连 | 成员互相污染上下文，结论无法归因 |
| 6 | 每阶段结束**通报进度**，把完整产出原文传给下一阶段 | 学生只看到最后一段，中间断链 |
| 7 | 任务列表 + 信箱 | 无法并行、无法认领、失败无法重试 |

前五条是**硬约束**，不是建议。不写进提示词，模型一定会走捷径。

## 7. 不要照搬的一条

WorkBuddy 的专家团是**任务型一次性流程**：投资分析走「采集 → 辩论 → 决策 → 风控 → 报告」，阶段固定，可以在提示词里写死 SOP。

营小商是**多轮对话**：学生随时插一句「那学习呢」「再讲讲」，没有固定阶段。硬套 SOP 会在第二次追问时打断对话。

真要上多 agent，正确的切法是**按需委派**（这一轮确实要并行取多个来源、或需要独立审查时才派），而不是每轮都走固定流水线。

## 8. 和代码的对应

| 概念 | 现在在哪 |
|---|---|
| 主提示词 | `packages/agent/agents/mentor.md` |
| 手册 | `packages/agent/references/*.md` |
| 手册索引 | `mentor.md` 的「手边的资料」一节 + `tools/read-tools.ts` 的 `read_reference` |
| 手册清单 | `prompts.ts` 的 `REFERENCE_NAMES` |
| 主循环 | `team.ts` 的 `runTeamTurn`（单循环，无成员） |
| 产物工具 | `tools/write-tools.ts` 的 `write_page` / `emit_question_set` |
| 已移除 | `MEMBERS`、`memberTool()`、`MEMBER_ARTIFACTS`、`memberEmitTools()` |
