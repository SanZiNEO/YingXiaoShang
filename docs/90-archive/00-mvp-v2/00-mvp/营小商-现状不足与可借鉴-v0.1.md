# 营小商 · 现状不足与可借鉴项（DSH）

> 配套：[`营小商-MVP-v2.0.md`](营小商-MVP-v2.0.md)、[`营小商-MVP-需求分层-v0.1.md`](营小商-MVP-需求分层-v0.1.md)。
> 本文不定义产品，只回答两件事：**我们现在差在哪**、**DeepSeek Harness（下称 DSH）里有现成的东西可以怎么借**。
> 结论先行：**先做单代理 + skill，不要继续加多代理。**

> **更新（2026-10-21，上下文与材料）**：第 6、7 条已按 DSH 机制落地（历史进 `messages`、工具结果保留/裁剪、`trace.context` 分类统计）；材料预取已退掉，system 只留知识点目录，正文由 `read_kp` / `read_material` / `read_textbook` / `read_news` 按需读。原因与验收见 [`20-features/知识点目录与按需读取-v0.1.md`](../20-features/知识点目录与按需读取-v0.1.md)。

| 5 | **提示词只能整份注入** ✅ | ~~`prompts.ts` 只做 `readFileSync` 全文读入，没有分层、没有按需加载~~ → 主提示词 170 行常驻，7 份手册按需读 | 角色一多就只能靠删内容控制体积 |

## 2. DSH 里可以直接学的

以下全部出自 `example/deepseek-harness-master` 的源码与文档。

| # | 机制 | 它怎么做的 | 我们怎么用 |
|---|---|---|---|
| L1 | **一个 loop，能力靠声明** | `packages/preset`：「The Host **shares the Agent loop**; each Agent sees the **tools, prompts and skills** of its selected revision.」 | 保留现有 `tool-loop.ts`（343 行），把"谁上场"从代码分支改成"选哪套 prompt + tools + skills" |
| L2 | **Skill = 按需加载的说明书** | `packages/skill`：技能是 `SKILL.md` + frontmatter（`name`、`description`），可带 `references/` 与 `templates/`；`.agents/skills/dsh-doc/` 就是这个形态 | 把现在 6 份角色提示词改写成 5 个 skill，正文不进上下文，模型需要时再加载 |
| L3 | **Skill 有目录和加载工具** | `packages/skill/tool-skill`：发布会话级 skill 目录 + 模型可调的 `skill` 加载工具，并支持 `/name` 直接调用 | 模型先看目录（一句话描述），自己判断该加载哪个 |
| L4 | **Skill 就绪靠注册表** | `ctx.skills` 合并多来源（文件系统/内置/远端），分层 host + per-scope，同名按 rank 去重；`skill-filesystem` 监视目录变更 | 加 skill = 放一个目录，不改代码、不重打包 |
| L5 | **工具定义有明确契约** | `docs/subsystems/tools.md`：`ToolDefinition` = 模型可见的 `ToolSchema` + 必需的标准输出声明 + `execute` + 调度元数据 + UI 呈现器；`schemas()` 用**显式 allowlist** 生成模型可见列表，内部字段不泄露 | 我们的工具照这个拆：对外只有名字/说明/参数，执行与呈现分离 |
| L6 | **交付物是"声明"不是"模板"** | `packages/deliverables`：`present` 工具「declares final files the model delivered」，workspace 变更另记，客户端在回合末渲染 | 用 `write_page`(html) + `present` 取代 6 个 `emit_*` 与六个渲染分支 |
| L7 | **上下文有压缩机制** | `packages/compaction`：自动压缩 + 按需 `/compact` + 工具输出裁剪 | 补上第 6、7 条不足：工具输出统一裁剪、长对话自动压缩 |
| L8 | **多代理组队是实验性的** | `packages/experimental/agent-team`：「The package is **experimental** and requires durable session storage.」同目录还有 `agent-team-profile`、`client-ui-agent-team` | 印证"先别上多代理"的判断 |
| L9 | **稳定的只有"委派"，不是"组队"** | `packages/subagent`：in-process（全新/带历史）、out-of-process（ACP/Codex/Claude Code）三种子代理，可继续子任务、可查状态 | 真需要并行取材料时，用委派而不是组队 |

## 3. 建议形态：单代理 + skill

```text
一个 loop（复用 tool-loop.ts）
   ├─ 常驻提示词：身份 + 硬规则（短，几十行）
   ├─ skill 目录：模型看到的是一句话清单
   │    ├─ 案例精讲      SKILL.md + references/（教材要点）
   │    ├─ 出题          SKILL.md + templates/（题目结构）
   │    ├─ 调研设计      SKILL.md + references/
   │    ├─ BP 大纲       SKILL.md + references/
   │    └─ 成长评价      SKILL.md + references/（能力 rubric）
   ├─ 工具（少而通用）：读材料 / 查课程 / 查新闻 / 写页面 / 出题 / 加载 skill
   └─ 输出：write_page(html) → present → 右栏渲染
```

四条规则：

1. **能力 = skill，不是 agent**。原来"5 个成员"变成"5 个技能说明书"，模型按任务自己加载，谁也不需要被代码指派。
2. **提示词分三层**：常驻（身份与硬规则）/ 按需（skill 正文）/ 参考（skill 的 references，模型二次按需读）。现在是把整份文件全量塞进 system。
3. **工具保持通用**。工具不认识"消费者行为"这种业务概念，只做"取材料""写页面"；业务全在 skill 里。
4. **章节可配置**。ch04、ch07 只是数据与 skill 参数，加一章不改代码。

## 4. 为什么先不上多代理

| 理由 | 依据 |
|---|---|
| DSH 自己把它放在 experimental，还要求持久会话存储 | L8 |
| 我们的多代理当前收益只是"分工提示词"，成本是 6 份提示词 + 成员白名单 + 调度分支 + 两套实现并存 | §1 第 1、4 条 |
| 单代理 + skill 同样能做到"换一套说明书做不同任务"，而且调试链路短、日志好读 | L2、L3 |
| 真需要并行时，委派比组队简单得多 | L9 |

**什么时候再考虑多代理**：同一轮确实要并行取多个来源、或需要独立审查时。届时应走 DSH 的 subagent 委派模型，而不是自定义成员表。

## 5. 迁移顺序（按最小改动排）

| 步骤 | 动作 | 落到的文件 |
|---|---|---|
| 1 ✅ | 删旧路径 | `handleTurn`、`judgePlan`、`subagents.ts`、`registry.ts`、`router.ts`、`chat.ts`、`inquiry.ts` |
| 2 ✅ | 专业内容变成按需读的文件 | 用现成的 `references/` 落地：5 份专业手册 + 原有 2 份扩成 7 份；主提示词只留一份索引。没有另建 `skills/` |
| 3 ✅ | 加载工具 | 复用已有的 `read_reference`，`REFERENCE_NAMES` 从 3 扩到 7 |
| 4 ✅ | 产物换通道 | `write_page`(html) + `emit_question_set`；5 个 `emit_*` 已退役。历史产物的渲染分支暂留（旧管线不再接线，但库里还有旧产物） |
| 5 ✅ | 工具改注册 | `tools/types.ts` 定 `ToolSpec`，`tools/read-tools.ts` / `write-tools.ts` 是声明清单，`tools/index.ts` 负责绑定 |
| 6 | 补上下文机制 | 工具输出裁剪 + 回合压缩（照 L7） |

第 2 步的落地方式和本文原来设想的不完全一样：原设想是新建 `skills/` 目录、每份 `SKILL.md` 带 `references/` 子目录；实际直接用了已经存在、已经被打包进客户端的 `references/` 加 `load_reference` 工具。效果一样（常驻一份索引、正文按需读），改动小得多。

每一步都能单独验收，不必一次做完。

## 6. 不做的

- 不引入 DSH 的 cordis 全家桶，只借机制，不搬框架。
- 不照搬 `agent-team` 的 inbox / task board。
- 不为任何一个 skill 写代码分支——skill 是内容，不是代码路径。
- 不把 skill 正文常驻进上下文，那和现在整份注入没区别。
