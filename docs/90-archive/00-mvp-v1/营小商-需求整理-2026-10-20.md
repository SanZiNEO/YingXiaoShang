### T2 右上角浮层关不掉（P0）

**现象**（截图 1）：点右上角图层图标弹出的「自动传入给营小商」卡片（章节 / 最近轮次 / 证据 / 最近产物）挂在窗口右上角，**挡住窗口的最小化 / 关闭按钮，且点别处不消失**；老师是反复点图标才关掉的。

**定位**：`apps/desktop/src/renderer/src/App.tsx:1123`

```tsx
<div style={{ position: 'absolute', right: 0, top: 27, width: 270, ... zIndex: 35 }}>
```

- 只靠"再点一次按钮"切换 `contextOpen`，**没有点击外部关闭、没有 Esc 关闭**；
- 用 `position: absolute` 贴在头部右侧，宽度 270px，窗口较窄或头部元素变多时会顶到窗口右上控制区；
- 同区域的章节选择菜单（`App.tsx:1088`）是同样写法，同一个问题。

**改法**

1. 抽一个通用浮层行为：**点击外部关闭 + Esc 关闭 + 打开另一个时自动关掉这一个**（章节菜单与上下文卡片共用）；
2. 面板与窗口边缘保持 8px 安全间距，最大宽高受容器约束（`overflow: auto`），不越出内容区；
3. 视觉上给"可关闭"的暗示（卡片右上角一个 × 按钮）。

**验收**：打开后点空白处即消失、Esc 即消失、点另一个图标自动切换；窗口缩到最小宽度（1080）时仍不遮挡控制按钮。

### T3 没接模型密钥时的报错文案（P1）

**结论：不是程序 bug，是老师那台机器没填 API Key。** 但界面不该把英文栈直接丢给老师看。

**现象**（截图 1）：界面出现黄字

```
Error invoking remote method 'learning:chat': Error: DEEPSEEK_API_KEY is not configured
```

**定位**

- 抛出点：`apps/desktop/src/main/llm.ts:88`（`if (!settings.apiKey) throw ...`）；
- 透出路径：`learning:chat` IPC（`apps/desktop/src/main/index.ts:357`）未做错误归类，渲染层原样显示 `error.message`。

**改法**

1. 主进程统一把错误映射为**可读中文 + 处理建议**：
   > 还没配置模型密钥。去右上角「设置」填入 DeepSeek Key，能力会完整打开。
2. 渲染层不再显示 `Error invoking remote method` 之类技术栈，技术详情落日志；
3. 设置页给一个"测试连接"按钮，老师填完当场知道通没通（当前要发一条消息才知道）。

**验收**：不填 Key 时界面只有一句中文提示，没有英文栈；填 Key 后能正常对话。

## 3.5 T6 为什么慢（2026-10-20 实测诊断）

**结论先说：这套东西确实是"自循环 agent"为主的架构，而且现在是"套娃循环"——外层 lead 循环里再套成员循环。**

### 3.5.1 架构现状

桌面端和 Web 端走的都是 `handleConversation` → `runTeamTurn`（`packages/agent/src/team.ts`）：

```
用户消息
 └─ runAgentLoop(maxRounds=10)          ← 外层：team-lead 自己循环
      ├─ 工具：case-coach / question-coach / strategy-advisor / growth-assessor / devil-advocate
      │    └─ runAgentLoop(maxRounds=10)  ← 内层：成员自己再循环
      │         └─ 工具：list_chapter_kps / read_kp / read_textbook / search_news / read_news
      └─ 工具：上面这些读工具（lead 也能自己查）
 └─ finalizeArtifacts → 生成 docx
```

- 外层 10 轮 × 内层 10 轮，**理论最坏 110 次模型请求**；
- 另有 `handleTurn`（规则 + 路由器 + 子 Agent）那条老链路还在仓库里，只有测试脚本在用，两条链路并存、口径容易漂。

### 3.5.2 实测数据（离线脚本，不含网络）

新增 `scripts/diagnose-loop.ts`：把一条最典型的"讲一个概念"跑一遍，统计每次请求带了多少上下文。

| 序 | 角色 | 系统提示 | 消息数 | 工具数 | 工具 schema |
|---|---|---|---|---|---|
| 1 | team-lead | 7007 字符 | 1 | 11 | 3065 字符 |
| 2 | member | 3712 字符 | 1 | 8 | 3006 字符 |
| 3 | member | 3712 字符 | 3 | 8 | 3006 字符 |
| 4 | member | 3712 字符 | 5 | 8 | 3006 字符 |
| 5 | team-lead | 7007 字符 | 3 | 11 | 3065 字符 |

**一句话问题 = 5 次串行模型请求，输入合计约 4.8 万字符（≈2.2 万 tokens），输出只有 600 字符。**

### 3.5.3 三个互相放大的原因

1. **串行**：5 次请求首尾相接，没有一次能提前出字。每次 3–6 秒，一轮 15–30 秒；遇到案例精讲要写产物，成员还要多跑 2–3 轮。
2. **重复上下文**：同一个 `environment()`（本章小节 + 最多 40 个知识点名 + 最近 8 条对话）被 lead 拼一次、**被每个成员再各拼一次**；同一成员的 3 轮请求里，3712 字符的系统提示 + 3006 字符的工具 schema 逐字重复 3 遍。实测重复注入约 1.26 万字符。
3. **没有流式反馈**：`DeepSeekLlm.stream` 实际是"整包等回来再一次性吐出"（`apps/desktop/src/main/llm.ts` 里先 `response.json()` 再 yield），界面只有一句「正在判断并整理…」。**响应其实没那么慢，是"什么都没发生"让人觉得慢。**

### 3.5.4 建议的改法（按性价比排序）

| 优先级 | 改动 | 预期效果 | 风险 |
|---|---|---|---|
| P0 | 最后一轮改成真流式，逐字推到界面 | 首字从 15–30s 降到 2–3s | 低（只改 IPC 通道） |
| P0 | 成员调用前先在代码里把材料取好塞进 task，省掉成员自己 2 轮读工具 | 5 次请求 → 3 次 | 中（要看质量是否变差） |
| P1 | `environment()` 每轮只算一次并缓存；成员 system 在同一轮内复用 | 省 1 万+ 字符/轮 | 低 |
| P1 | 同名同参数的工具调用直接复用上次结果；lead/member 的 `maxRounds` 降到 6/5 | 防"绕圈"和跑偏 | 低 |
| P2 | `read_textbook` 里 `listContentTags({limit:100000})` 改为按块查 | 少扫全章标签 | 低 |
| P2 | 停掉/收编旧的 `handleTurn` 链路 | 减一套口径 | 中 |

### 3.5.5 改完之后的实测（2026-10-21，真模型 deepseek-chat）

| 场景 | 改之前 | 改之后 | 产物 |
|---|---|---|---|
| 概念问答（"为什么直播氛围促冲动消费"） | 45s，首字 30s 无输出 | **6.4s，首字 1.7s**，2 次请求 / 1 次工具 | 不需要 |
| 出题（"出 3 道消费者行为选择题"） | 70s 以上，产物 0 份 | **31.9s**，11 次请求 / 10 次工具 | **1 份 question_set，3 题，0 告警** |
| 案例精讲（"用直播带货做一份案例精讲"） | 45–200s，常在产物处失败 | **62s** | 1 份 case_study docx，0 告警 |

### 3.5.6 2026-10-21 定位到的四个真原因（按影响排序）

前一轮诊断只看到"串行 + 重复上下文 + 假流式"，实际跑下来发现真正吃掉时间的是下面四条，
其中第 4 条是"读完材料不动笔"的根因。

1. **假流式**（已修）：`DeepSeekLlm.stream` 先 `await response.json()` 再一次性 yield。
   改成真 SSE（`stream:true` + `TextDecoder` 增量按行解析 `data:`），首字从 30s 降到 700–1700ms。

2. **产物 JSON 被输出上限截断，模型无限重试**（已修）：`emit_case_study` 想一次写 15KB JSON，
   超过 `maxTokens: 8192` 被截断成非法 JSON（`Unterminated string in JSON at position 15545`），
   模型看到"工具执行失败"就重写一遍，又截断——单轮烧掉 200 秒。
   改法：emit 工具支持分段写入 + 按知识点名/题干合并；截断时报错文案明确要求"拆成 2–3 次"。

3. **读工具重复交付同一批内容**（已修）：模型读完一段换个关键词再读，永远有下一段，永远有正反馈。
   改法见 3.5.7 第 2 条。

4. **"结束"可以绕过"交付"**（已修，根因）：学生要产物时，成员只要写一段正文就能结束本轮，
   产物写没写无所谓。所以它读起来没有尽头。
   改法见 3.5.7 第 3 条。

另外还有一个低级错误，单独列出来：产物意图的正则里没有"选择题"。
学生说「出 3 道…选择题」，匹配不到 `出题|题目|试卷` 任何一个，产物工具根本没挂上——
**之前几十次"产物 0 份"都是这一个原因**。已补全（选择题/判断题/简答题/练习题/测验/考试/出 N 道…）。

### 3.5.7 三处改法参照的公开实现

这三条不是自创，是照着成熟 agent 的做法改的，出处在下面，方便以后核对：

| 改法 | 参照 | 公开依据 |
|---|---|---|
| 每轮由程序注入进度/环境事实（`status`） | Cline / RooCode / Devin 的 `environment_details` | Cline 系统提示原文："At the end of each user message, you will automatically receive environment_details. This information is not written by the user themselves, but is auto-generated…" |
| 读过的内容不重复返回，只回一句"未变化，去引用上文" | Claude Code `Read` 的 `file_unchanged` | 返回固定串：`File unchanged since last read. The content from the earlier Read tool_result in this conversation is still current — refer to that instead of re-reading.`；按 (path, offset, limit, mtime) 判重，写入后缓存失效 |
| 交付工具是结束任务的唯一出口（`requireWrite`） | Cline 的 `attempt_completion` | Cline 系统提示里 `attempt_completion` 是专门的完成工具，参数 `result`，且要求"不要以提问结尾" |

注：Cline 的 `environment_details` 注入的是**环境事实**（文件树、活跃终端、linter 报错），
我们注入的是**本轮进度事实**（读了几次、派了谁、产物有没有写入）——同一个机制，换了适配的内容。
