## 反馈 001：空态建议看起来像固定内容

### 1.1 用户原话

> “给我的感觉，这里是固定的内容吗？”

附截图：空态标题为「接着「消费者市场与购买行为分析」往下走」，说明为“你正在学…已有 9 条证据…”，下方三个按钮：

- 用胖东来案例讲“消费者”
- 消费者市场是什么
- 用第4章分析最新新闻

### 1.2 核验结论

**不是完全固定，但也不是每次自由生成；当前是“按状态规则生成”的模板。**

代码路径：

| 层 | 位置 | 行为 |
|---|---|---|
| 后端生成 | `packages/agent/src/index.ts` → `AgentService.suggestions()` | 读 `LearningStateSnapshot`，按 phase / scope / 证据数 / 最近产物 / 新闻状态生成标题、说明和 2–3 个入口 |
| 前端渲染 | `apps/desktop/src/renderer/src/App.tsx` 空态 | 渲染 `suggestions.title / description / items`；接口失败时才用固定三条 `SUGGESTIONS` 兜底 |
| 测试 | `scripts/test-case.ts` | 校验 suggestions 标题与案例入口 |

会随状态变化的部分：

- 标题：`pre` 是“先把起点摸清”；`learning` 是“接着「章节」往下走”；`post` 是“把学到的判断迁移一次”；有未完成研究设计时优先“继续改研究设计”。
- 说明：带当前章节、证据数。
- 按钮：有最新新闻时出现“用第4章分析最新新闻”；否则给情境题；有研究设计时给“继续改研究设计”。

**为什么看起来固定：**

1. 同一状态下规则输出稳定：同一个 phase/章节/证据数/新闻状态 → 同一组标题和按钮。
2. 当前没有“换一组”或“为什么是这三个”的可见解释。
3. 三个按钮是规则模板，不是 LLM 每次生成的多样化建议。
4. 截图里的状态刚好是 learning + ch04 + 9 条证据 + 有新闻，所以命中了同一套模板。

### 1.3 用户感受的合理性

用户感觉“固定”是合理的，因为：

- 视觉上只有一组建议，没有状态依据；
- 同一学生连续打开几次，看到的还是同一组；
- 按钮文案比较像产品预设，而不是“根据你刚才的学习生成的”。

### 1.4 建议的改进

按优先级：

1. **显示“为什么是这三个”**  
   在空态下方加一行轻量说明，例如：`依据：学习中 · 第4章 · 9 条证据 · 有最新新闻`。  
   不暴露 phase/intent 等内部枚举，只显示学生能理解的状态。

2. **加“换一组”**  
   同一 snapshot 下维护一个小候选池，点击“换一组”轮换 2–3 个入口；不重复当前组。  
   候选池仍由规则生成，避免模型成本和不可控。

3. **让建议更贴上一轮**  
   如果最近一轮是案例，优先“继续追问案例里的某个知识点”；如果最近有错题，优先“只练错题”；如果有未完成产物，优先“继续改产物”。

4. **可选：LLM 生成建议**  
   在规则候选不足或学生连续两次“换一组”后，让 ChatAgent 生成 2–3 个建议；必须校验：不暴露内部字段、必须具体到当前章节/概念/产物、失败回退规则。  
   不建议默认每次空态都调 LLM，成本和延迟不划算。

5. **空态反馈入口**  
   允许学生对建议点“不相关”，记录到 `memory_facts` 或反馈表，下一轮调整候选。MVP 可以先不做，但预留字段。

### 1.5 状态

- 当前实现：规则 + 状态插值；固定三条仅兜底。
- 用户反馈：已记录。
- 处理建议：待产品确认是否做“换一组 / 状态依据 / LLM 建议”。
- 不在本轮直接改代码，避免在没有确认交互前继续加复杂度。

## 反馈 003（历史，已处理）：聊天上下文不连贯

### 3.1 用户原话

> “给我的感觉是你这个 chat 没有做连贯上下文这个处理。”

### 3.2 核验

属实。此前：

- `ChatAgent.chat` 读了最近消息，但 `synthesize` / `ask` / `plan` 没带最近对话；
- Router 只看当前消息和状态，不看上一轮；
- 案例追问“那学习呢”会重新展开整份案例。

### 3.3 已处理

- Router 带最近 8 条 user/assistant 消息；
- ChatAgent 的 `chat / ask / plan / synthesize` 都带最近 10 条；
- 知识解释的短追问会把上一条用户消息拼进检索 query；
- 案例追问返回 `focusKpIds`，只展开被追问的知识点；
- UI 对知识步骤也会打开“依据”标签。

### 3.4 验证

- `pnpm test:context`：第一轮案例 → “那学习呢”只展开学习 → “消费者市场”追问只展开消费者市场 → 开放聊天能拿到最近消息。
- `pnpm test:ui-case`：真实 Electron UI 发送“那学习呢”，仍保持学习知识点与定义先行结构。

## 反馈 005：同一问题与两家系统对比，问题在 Agent 设计

### 5.1 用户原话

> “还是我们的 agent 设计的问题，你懂吗？现在你先整理文档，将这个对比给写到反馈文档里。”

### 5.2 对比问题

```text
永辉、胖东来、步步高都在卖生鲜和日用品。为什么进店买东西的人都是消费者，而不是组织市场？他们在购买中可能分别扮演哪些角色？如果一位顾客从“顺路买”变成“跨城打卡”，这算消费者学习还是品牌忠诚？请给出判断标准和一个反例。
```

### 5.3 三家回答概览

| 系统 | 回答覆盖 | 主要优点 | 主要问题 |
|---|---|---|---|
| A 家 | 消费者 vs 组织市场、五种购买角色、学习 vs 忠诚、反例 | 三个机制解释为什么不是组织市场；完整列出五种角色；过程/结果 + 判断表 + 反例 | 偏通用知识，没有课程证据 |
| B 家 | 学习 vs 忠诚 | 把“过程 vs 结果”讲透；五维对比表；三步判断；两个误区；判断公式 | 对“消费者/组织市场/角色”展开较少；没有课程证据 |
| 营小商 | 消费者、消费者市场、学习 | 课程定义准确；案例落地；边界清楚；4 条依据；有追问 | **没有回答购买角色**；学习 vs 忠诚很浅；追问聚焦错；固定三点模板；案例对话是预置脚本 |

### 5.4 具体差距

1. **购买角色完全缺失**
   - A 家完整列出：发起者、影响者、决策者、购买者、使用者，并说明单人场景可能一人承担全部角色。
   - 营小商没有回答这一块，因为 `case-library.ts` 只有消费者、消费者市场、学习三个知识点，没有“购买决策参与者”。

2. **“为什么不是组织市场”不够系统**
   - A 家从商品属性/包装、选址/客群、价格/交易模式三个机制解释，并补充小餐馆临时采购的例外。
   - 营小商只讲“最终用途”和“开餐馆买土豆”的例子，正确但单薄。

3. **学习 vs 忠诚没有真正展开**
   - B 家用“过程 vs 结果”、五维对比、三步判断、两个误区、判断公式，把区别讲透。
   - 营小商只讲了“学习看行为规则有没有变”，对“品牌忠诚”只有一句边界；追问“消费者学习 vs 品牌忠诚”时，甚至错误聚焦到“消费者”。

4. **追问聚焦错误**
   - 用户追问：“那‘消费者学习’和‘品牌忠诚’到底怎么区分？”
   - 营小商回复：“接着上一轮，你问的「消费者」这张卡……”
   - 原因：`CaseCoach` 用字符串包含 + 名称长度排序；“消费者学习”同时包含“消费者”和“学习”，选中了更长的“消费者”。

5. **固定案例脚本冒充实时对话**
   - 案例卡里的“学生提问”是 `case-library.ts` 预写的，不是用户真实提问。
   - 不管问什么，都会展开同样的三张卡；对话、结论、边界都是固定的。

6. **Prompt 重结构、轻覆盖**
   - Prompt 要求“3–5 个知识点 → 2–3 条迁移 → 边界 → 检查问题”。
   - 但没有要求“用户问了几块，必须逐块回答”。
   - 结果：结构完整，内容缺块；简单题也被套成三点式。

7. **数据层支撑不足**
   - `content_tags = 0`：教材段落没有标签；
   - `news_tags = 1`、`case_matches = 1`：新闻/案例匹配几乎是 mock；
   - ch04 有 6 组同名知识点，匹配投票被拆散；
   - UI 仍显示 `core` / `kp_*` 英文或内部 ID。

### 5.5 根因：Agent 设计，不是模型能力

| 层 | 问题 | 结果 |
|---|---|---|
| 路由 | 多部分问题被 `CASE_PATTERN` 一票路由到 `case` | 购买角色、品牌忠诚没有进入计划 |
| 内容供给 | `case-library` 只有三个知识点 | 模型拿不到角色/忠诚材料，只能重复消费者 |
| 计划 | 没有“问题拆解 + 覆盖检查”步骤 | 答完一部分就进入模板收尾 |
| 聚焦 | 字符串包含 + 长度排序 | 追问“消费者学习”错误聚焦到“消费者” |
| Prompt | 结构约束优先于覆盖约束 | 每轮都是三点 + 三条 + 边界 |
| 数据 | 教材 tags 未生成、KP 重复、英文标签 | 检索和证据层不可靠 |
| 评估 | 没有“是否答全”的验收 | 结构完整但内容缺失也能通过 |

### 5.6 结论

**不是模型不会答，是 Agent 设计把题交给了错误的角色，又没有给足材料。**

这道题需要的是：

1. 先拆成“消费者/组织市场”“购买角色”“学习/忠诚”“反例”四个子任务；
2. 一部分走 `case`（案例落地），一部分走 `knowledge`（角色、忠诚、判断标准）；
3. ChatAgent 汇总时做覆盖检查，逐块回答；
4. 最后才做教练式追问，而不是用固定三点收尾。

当前实现是：

```text
多部分问题 → case 固定讲义 → 三点模板 → 追问聚焦错
```

所以用户感觉“不如人家”，是合理的。

### 5.7 下一轮验收建议

- 同一问题必须覆盖四个子任务，缺一项即不通过；
- 必须出现五种购买角色；
- 必须给出学习 vs 忠诚的判断标准和反例；
- 不允许用固定案例卡替代回答；
- 追问“消费者学习 vs 品牌忠诚”必须聚焦“学习/忠诚”，不能回到“消费者”；
- 标签必须中文，不能出现 `core` / `kp_*`；
- 回答结构随题型变化，不强制三点。

## 反馈 006：对照《营销课程碎片化知识体系》设计，当前实现明显退化

### 6.1 用户原话

> “回看这份文档，这份文档当时的设想都比我们现在的好，你看完，然后再去优化之前的那个反馈文档。”

对应文档：`docs/20-features/营销课程碎片化知识体系-设计与标注规范-v0.1.md`

### 6.2 设计文档的核心设想

这份文档不是“功能设想”，而是一套完整的数据规范：

```text
课程 → 模块 → 单元 → 知识点 → 内容块 → Tag
```

关键原则：

1. **知识点是最小可教/可评概念**，一个概念只保留一个主 ID，其他叫法进 aliases。
2. **内容块是段落/表格/图**，1–3 段，保留 `position/page/source`，不切到句子级。
3. **Tag 是受控连接**，不是自由关键词；命名空间包括 `knowledge_point / competency / decision / context`。
4. **tag_role 有权重**：`core 1.0 / example 0.7 / mention 0.3`。
5. **证据分级**：`gold`（教材人工审批）/ `verified`（AI 预标 + 人审）/ `auto`（只做召回）。
6. **每条 tag 必须带** `confidence / method / evidence_span / review_status / version`。
7. **教材 tag 人工立法，爬取 tag AI 执法**：双人标注、仲裁、抽样复核、冻结版本。
8. **匹配是三段式**：tag 倒排召回 → 向量召回 → 排序 + 多样性 + 质量过滤 → LLM/教师复核。
9. **匹配结果不是答案，只是候选**；`auto` tag 不能直接用于高利害评价。
10. **质量指标**：教材覆盖率 ≥95%，匹配 precision@5 ≥0.8，双人一致率 ≥0.75。

### 6.3 当前实现对照

| 设计要求 | 当前实现 | 差距 |
|---|---|---|
| 教材内容块打 tag | `content_blocks` 744 段，`content_tags` **0 条** | 教材段落完全没有标签 |
| 每个知识点一个主 ID | ch04 有 6 组同名知识点 | 概念分裂，匹配投票被拆散 |
| 每块 1–3 个 tag | 无块级 tag | 无法按段落召回 |
| 文章聚合 3–8 个 tag | `news_tags` **1 条** | 几乎等于没有 |
| tag_role 权重 | enum 有 `core/example/mention`，但 UI 直接显示英文 | 有字段，无中文显示、无权重排序 |
| 证据分级 gold/verified/auto | 没有落地 | 教材、新闻、规则结果混在一起 |
| evidence_span 原文校验 | 案例证据的 `sourceId` 全部指向同一篇不相关文章 | 证据链不可信 |
| 双人标注/仲裁/抽样 | 没有 | 没有 gold 集，没有一致率 |
| AI 打标 + 规则校验 | `Matcher` 有 prompt，但 `case_matches` 只有 1 条 mock | 没有真实跑过 |
| 三段式匹配 | 关键词/评分/topK，没有向量召回和排序公式 | 匹配虚高、不可解释 |
| 质量指标 | 没有 precision@5 / 覆盖率 / 一致率 | 无法判断好坏 |
| 匹配结果只是候选 | 案例精讲直接自动打开、当答案用 | 把候选当结论 |
| 教材覆盖率 ≥95% | 0% | 完全未达标 |
| 文章 tag 3–8 | 1 | 完全未达标 |

### 6.4 为什么这会导致用户看到的现象

用户看到的几个问题，都能从这张表解释：

1. **“tags 是英文的”**  
   `tag_role` 是 `core/example/mention`，UI 没有做中文映射；`tag_key` 还是 `kp_*`。

2. **“匹配度不高”**  
   没有块级 tag，只能靠关键词/评分/topK；没有向量召回、没有 tag 权重、没有质量过滤。

3. **“很多东西本来不应该存在”**  
   案例证据的 `sourceId` 全部回退到 `caseNews[0]`；`案例事实归纳` 不是来源，却带“查看原文”；对话是预置脚本，不是实时生成。

4. **“不是模型生成，是阈值的”**  
   案例产物是 `SUPERMARKET_CASE` 的固定对象；阈值只决定“走不走 case、挂哪条引用”，不决定内容。

5. **“知识点很多但很乱”**  
   设计建议每单元 3–8 个知识点；当前 ch04 有 50 个，其中 6 组同名。不是更细，是缺少治理。

### 6.5 设计文档里最值得恢复的四件事

1. **先补 `content_blocks → content_tags`**  
   教材段落是 gold 证据层；没有它，所有解释都只能靠定义和关键词。

2. **恢复 tag 的受控语义**  
   - `knowledge_point / competency / decision / context` 四个命名空间；
   - `core/example/mention` + 权重；
   - `confidence/method/evidence_span/review_status/version`；
   - UI 中文映射，禁止 `core` / `kp_*`。

3. **恢复匹配的三段式**  
   - tag 倒排召回；
   - 向量召回；
   - 排序公式 + 多样性 + 质量过滤；
   - 结果带 tag/role/evidence/source/score。

4. **恢复“匹配是候选，不是答案”**  
   - `auto` 只做召回；
   - `verified` 才能进教学；
   - `gold` 才能做评价锚点；
   - 案例精讲如果还是预置资产，应标注“教师示范”，不要冒充实时回答。

### 6.6 结论

这份设计文档的设想确实比当前实现完整：

- 它把“知识点、内容块、标签、证据、匹配、质量”拆清楚了；
- 当前实现只保留了表结构和部分字段，**没有真正跑标注，也没有按标签匹配**；
- 于是系统退化成“关键词 + 固定案例 + 错误引用”。

所以问题不是“设计不够好”，而是**实现没有按设计落地**。

### 6.7 下一轮验收建议（标签层）

- `content_tags` 覆盖率：ch04 ≥95%；
- 每个内容块 1–3 个 tag，且每个 tag 有 `evidence_span`；
- 每条 tag 的 `evidence_span` 必须能在对应 `content_block.text` 中找到；
- ch04 同名知识点合并为单一主 ID，其他进 aliases；
- `news_tags` / `case_matches` 不再使用 mock；至少跑完 20 篇真实文章；
- UI 标签全部中文：核心/例证/提及、知识点/能力/决策/情境；
- 匹配结果带 tag、role、evidence、source、score，不再只显示 `core`；
- 案例证据的 `sourceId` 必须与 quote 对应，禁止 `caseNews[0]` 兜底；
- 质量指标：precision@5、教材覆盖率、双人一致率至少有数。

## 附录 A：标签与回答质量评估（合并）

### A.1 标签数据现状

| 表 | 数量 | 说明 |
|---|---:|---|
| `content_blocks` | 744 | 教材段落/表格/图，ch04 47 段 |
| `content_tags` | **0** | 教材段落标签完全没有生成 |
| `news_tags` | **1** | 仅 1 条 mock |
| `case_matches` | **1** | 仅 1 条，`rationale = 'mock evidence'` |

- ch04 有 6 组同名知识点；
- `tag_role` 是 `core/example/mention`，UI 直接显示英文；
- 案例证据的 `sourceId` 全部指向同一篇不相关文章；
- “案例事实归纳”不是来源，却带“查看原文”。

### A.2 回答“每次三点”的原因

`packages/agent/src/chat.ts` 的 system prompt 明确要求：

```text
3–5 个知识点
2–3 条可迁移结论
边界条件
一个检查问题
```

所以内容会变，但形状不变；不是文本硬编码，是结构硬编码。

### A.3 同题对比（消费者/组织市场/购买角色/学习 vs 忠诚）

| 维度 | 另一系统 A | 另一系统 B | 营小商 |
|---|---|---|---|
| 消费者 vs 组织市场 | 三个机制 + 例外 | 有 | 只讲最终用途 |
| 五种购买角色 | 完整 | 未展开 | **缺失** |
| 学习 vs 忠诚 | 过程/结果 + 表 + 反例 | 五维 + 三步 + 误区 | 很浅 |
| 课程定义 | 有 | 有 | **最准确** |
| 案例落地 | 一般 | 一般 | **最好** |
| 证据引用 | 无 | 无 | **4 条** |
| 追问 | 有 | 有 | 有，但聚焦错 |
| 自然度 | 高 | 高 | 模板感强 |

结论：对方赢在知识覆盖和自然表达；营小商赢在课程定义、案例落地、边界、证据和追问。当前回答是“好教练”，但不是“完整答完问题的老师”。

### A.4 根因

1. 路由把多部分问题一票交给 `case`；
2. 案例库只有三个知识点，没有购买角色/品牌忠诚；
3. Prompt 重结构、轻覆盖；
4. 追问聚焦用字符串包含，错误选中“消费者”；
5. 教材段落标签为 0，匹配靠关键词；
6. 案例产物是固定对象，不是模型生成。
