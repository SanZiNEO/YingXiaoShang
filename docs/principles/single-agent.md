# 营小商 · 设计原则

> 这份文档是**唯一的设计原则**。所有需求文档（`docs/requirements/`）和 MVP 口径（`docs/mvp/`）都必须服从它；
> 与它冲突的设计、代码和旧文档，一律以本文为准。
>
> 一句话：**一个智能体，提示词管判断，工具管能力，skill 管判据，上下文由模型按需取。**

---

## 1. 只有一个智能体

- **从始至终只有一条主循环、一个说话人。** 没有子代理、没有角色切换、没有专家选择器、没有按意图路由到不同 agent。
- 学生看到的永远只有「营小商」一个人。内部分工不体现在界面上，也不体现在称呼上。
- 允许的内部分工只有三种存放方式：
  1. **提示词里的判断规则**（什么时候讲、什么时候追问、什么时候产附件）；
  2. **工具**（真实数据、副作用、结构化结果）；
  3. **skill / 手册**（判据与方法论，模型按需读）。
- **禁止**：为某个能力单独起一个 agent、单独拼一套 system prompt、单独开一条调用路径；
  也禁止把这些分工名（教练 / 导师 / 专家 / 子智能体）暴露给学生。

判据：如果一项新功能需要「再加一个会说话的东西」，它就不合规；它应该变成工具或 skill。

---

## 2. 功能只有三种落位

任何需求落地前先回答：**它属于提示词、工具，还是 skill？** 三者都不是，就不做。

| 落位 | 判据 | 典型内容 |
|---|---|---|
| **提示词** | 需要判断、取舍、语气、边界；不需要真实数据 | 身份与边界、什么时候产附件、怎么追问、HTML 约束 |
| **工具** | 需要真实数据、副作用、结构化结果；结果要被系统接着算 | 读知识点、读教材、搜新闻、读新闻、写页面、出题 |
| **skill / 手册** | 「做到什么程度算合格」的判据；具体方法论长文 | 案例精讲判据、出题判据、调研/BP 手册、评价 rubric |

**禁止第四种落位：把业务判断写进代码。** 包括但不限于：
按关键词/正则判断学生意图、为某个品牌或某条新闻写分支、给每类产物配一套模板与渲染器、
把「第 4 章」「消费者行为」写死在调度逻辑里。

加一个能力 = 加一条工具声明 + 在提示词里说一句它什么时候用；或者加一份 skill + 在提示词里说一句何时读。
不牵动主循环，不改别人的参数。

---

## 3. 上下文按需取，不预塞

- system 里只放**稳定指令 + 运行时事实 + 目录**。目录只给名称和一句话，明确标注「不是原文，不能当引用」。
- **正文、原文、新闻全文、题库、历史产物，一律由模型调工具读。**
- **禁止预取业务材料**：不由代码替模型挑知识点、拼原文、塞进 system。
- **禁止假已读**：不把预取内容标成「本轮已读」来阻止模型重读。
- 引用必须来自工具返回的原文；目录、摘要、模型常识都不能冒充教材原文。
- 工具返回有长度上限；超了截断并说明还剩多少，不把整本书塞进上下文。

判据：如果一段内容「每轮都出现」，它要么是稳定指令，要么是目录；否则应该变成工具。

---

## 4. 工具的形状

- **自描述**：名字、说明、参数 schema 都在工具身上，模型看得懂就会用。
- **白名单**：只有注册过的能力。没有 shell、没有任意命令、没有任意 URL 抓取。
- **面向领域说人话**：对外是「给我 ch04 消费者动机的材料」，不是「给我 kp_id 列表」；内部 id 由工具自己翻译。
- **无状态**：工具不持有本轮状态；状态由主循环传入。
- **可增删**：加能力 = 往清单里加一条，不牵动调度。
- **有界**：单次返回有预算，防止上下文被一份材料吃满。

---

## 5. 产物与输出

- **默认在聊天里讲完**：结论先行 → 拆解 → 迁移 → 边界 → 一个检查问题。
- **只有学生明确要「能带走的东西」时才产附件**；不要每轮都产，右栏不是阅读器。
- 产物默认是**单文件 HTML**：内联样式、无 `<script>`、无外链、320px 起不横向滚动、不重复标题。
- **唯一的结构化例外**：需要学生动手、且操作结果要被系统接着算的（目前只有出题）。
- 产物是下一轮判断的输入，不是终点。

---

## 6. 数据与边界

- 单学生、本地 SQLite；不做登录、多租户、教师端（这些属于 backlog，不进 MVP）。
- 不编造：没有证据就说证据不足；引用要能回到原文段落。
- 学生看不到内部枚举、置信度、工具调用日志、步骤 read/write、分工名。
- 对外只说「营小商」；不出现学校名；不说小程序，说桌面软件。

---

## 7. 判断一次改动是否合规：五问

1. 是否新增了第二个会说话的东西（agent / 角色路由 / 专家选择）？
2. 是否把业务材料预塞进了 system，或把预取标成「已读」？
3. 新功能是否落在提示词 / 工具 / skill 三者之一，还是写成了代码里的业务分支？
4. 学生是否能看到分工名、内部状态或工具名？
5. 是否为某个品牌、某条新闻、某一章写了特例？

任何一条回答「是」，改动就不合规，退回重做。

## 8. 现状与差距（只列方向，细节见需求文档）

| 现状 | 违反哪条 | 去哪看 |
|---|---|---|
| `packages/skills`、`subagents.ts`、`team.ts`、`news-lab.ts` 等旧多角色/旧管线仍在仓库 | §1 | R01、R04 |
| 旧 Web 面（`packages/ui`）与 `packages/bundle` 的 preset 仍按四个「专家」组织 | §1 | R01、R16 |
| 旧产物仍有 5 个结构化渲染分支与模板 | §2、§5 | R15 |
| 文档把「分工」当产品结构写（多专家团、角色设定） | §1、§7 | R01、backlog |
| 提示词里同时存在主提示词、skill、手册三套判据，边界不清 | §2 | R02、R04 |

**收敛方向**：先把文档口径统一到本文，再按 `docs/mvp/` 的清单逐项改代码；改代码前不新增任何第二种说话人。
