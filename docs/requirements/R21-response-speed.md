# R21 响应速度

> 状态：MVP（本轮）
> 依赖：R16（对话界面）、R18（模型运行时）、R01（单一智能体）
> 代码：`apps/desktop/src/renderer/src/App.tsx`、`apps/desktop/src/main/llm.ts`、`packages/agent/src/tool-loop.ts`
> 上位原则：[`../principles/single-agent.md`](../principles/single-agent.md)、[`../agent-runtime-audit-and-rebuild-guide.md`](../agent-runtime-audit-and-rebuild-guide.md)

## 1. 要什么（学生可见结果）

- 发出去之后，**马上能看到「收到了、正在干什么」**，不是一片静止的「正在判断并整理…」。
- 第一段**有用的话**要早出现；出了的字**不能又消失**。
- 等太久或者不想等了，**能点停止**；已显示的字和已提交的附件不会因此丢。
- 切到别的会话再回来，原来那轮的结果还在**原来那个会话**里。

老师的话是「发个消息他要转半天」，学长的判断是分两层治：**客观耗时**与**主观观感**。

## 2. 落位（提示词 / 工具 / skill / 数据）

**不属于提示词。**「回答快一点」这类描述解决不了耗时，只会让模型把该查的事实跳过。

**不属于 skill。** 判据解决不了耗时。

**属于界面事件契约 + 模型运行时**（R16、R18）。按审计 §4.9.1，事件的语义边界保持不变，只是不再由宿主自己推测完成状态。

**明确不做的事**：不加固定轮次、请求总数、工具总数、整任务时长上限（审计 §4.4.3）。
`maxRounds` 与「轮次用完强制收口」随原生 loop 切换一并删除（审计 F03）。

## 3. 行为（一轮里怎么发生）

现状（已存在，别重复造）：

1. 学生发送 → 写入 `stream.step = '正在判断这一句该怎么接…'`（`App.tsx:910`）。
2. 每轮向 `llm.stream()` 请求（`tool-loop.ts:232`），文本增量用 `emit({type:'text'})` 推出。
3. 工具调用前推 `emit({type:'tool-start'})`（`tool-loop.ts:309`），界面映射成中文阶段（`App.tsx:725`）。
4. 每轮开始推 `emit({type:'round'})`（`tool-loop.ts:379`），界面显示「正在组织回答…」（`App.tsx:731`）。

**问题就在第 3 步之后**：`tool` 事件一到，界面把已出的字清空（`App.tsx:723-726`）：

```ts
// 负责人已经吐过字又决定继续查资料：收回这段，避免半截话上屏。
const reset = item.agent === 'lead' ? '' : current.text
```

学生看到的就是「字出来了 → 没了 → 再等」。`tool-end` 事件界面也没处理。

要补的：

5. **不撤字**：已显示的文字保留为上一段，阶段单独一行显示；最终消息只提交一次。
6. **真实阶段**：消费 `tool-end`，工具跑完就更新为「已取到 xxx」，不是一直挂着「查资料」。
7. **可取消**：请求带 `signal`，主进程按 requestId 取消对应那一轮，不是全局杀服务。
8. **终态如实**：`finish_reason` 保留 `stop/tool-calls/max-tokens/aborted/error`，EOF 没有合法终态不能伪装成功。

## 4. 契约（事件语义、指标）

**界面需要表达的语义**（沿用审计 §4.9.1，不是另造一套运行时事件）：

| 类别 | 用途 |
|---|---|
| `started` | 立即确认 requestId / sessionId / turnId，用户消息已收下 |
| `stream start` | 模型请求已开始——不等于「已经有答案」 |
| `text delta` / `message end` | 分段维护可见文本，完成后与持久消息对齐 |
| `tool start` / `tool end` | 维护真实阶段；工具原名、内部参数、原文 preview 不上屏 |
| `artifact staged` / `committed` / `failed` | 附件的真实生命周期 |
| `terminal` | 成功 / 部分完成 / 失败 / 取消及原因，**无论哪条路径都恰好一次** |

**三种「快」分开记**（审计 §4.9.2）：

1. 发出消息到**有可信状态反馈**多久
2. 到**第一段有用答复**多久（不是一个标点，也不是「我来看看」）
3. 到**整个回合完成且可持久恢复**多久

按任务类别分别记录：身份问答、单概念解释、新闻分析、题目集。
每类记：请求数、首帧、首段有效答复、总完成耗时、是否输出截断、是否取消、请求 context 大小。

## 5. 边界（不做什么）

- **不设固定轮次/请求数/工具总数/整任务时长上限**。请求数是诊断数据，不是达标配额。
- **不为指标好看把复杂任务压成同样短的回答**。复杂任务只要确有进展就允许继续。
- **不做假进度、不做假流式**：不能先整段生成再打字机回放。
- **不靠撤字制造整洁**：正文说完又去查资料时，保留已说的话，另起阶段。
- **不为提速砍自检**：R10 的引文可回溯不能因为快就被跳过。
- **不引入第二个说话人**（R01）。

## 6. 验收

- [ ] 工具调用前后，已显示的文字**不会被清空**（对照 `App.tsx:723-726`）
- [ ] `tool-end` 到达后阶段行会更新，不再一直显示「查资料」
- [ ] 点停止：不再发起新的模型请求和工具，已显示内容保留，标为「已停止」
- [ ] `finish_reason` 为 `max-tokens` 时界面如实说明，不当作完整答复
- [ ] 网络 EOF / 空回复有准确失败，无无限等待
- [ ] 运行中切换会话：晚到事件只更新所属会话，不串字
- [ ] 四类任务各自的「首段答复」「总耗时」有实测记录（不是平均值混算）
- [ ] 连续三轮工具调用能自然继续，不出现额外强制总结

## 8. MVP 范围与后续

**MVP（本轮）**：跟随原生运行时切换落地，不单独做一版。

1. 事件语义按第 4 节接通（含 `tool-end`、`terminal` 恰好一次）
2. 停字/撤字问题修复（第 3 节第 5 条）
3. 取消链路（第 3 节第 7 条）
4. 三类耗时与请求数按任务类别记录

**后续（不排期）**

- 工具并行（需工具声明真实并发安全性）
- 领域读工具的进程内缓存（是读取优化，不是「读过就不许再读」的控制）

**触发条件**：以上不做，直到事件契约接通——先把「看起来在转圈」这类观感问题从源头消掉，再谈数字。
