# 新闻线：从「每台电脑各自爬」到「服务端定时入库 + 工具取」

> 状态：**第 1 步已实现（`5267ca9`），第 2、3 步未做**。依据：学长 2026-11-07 的建议 + 仓库现状核查。
> 对应现象：只要涉及联网查证就慢、时快时慢。

---

## 一、现在的实际形态（先纠正一个误解）

不是「没有爬虫」，而是**爬虫在客户端**：

| 已有 | 位置 | 说明 |
|---|---|---|
| 5 个新闻源抓取 | `packages/news/src/sources/`（brandstar / linkshop / socialbeta / wscn / web） | 有 `refresh()` 全量刷新 |
| 定时任务 | `apps/desktop/src/main/index.ts:94 startNewsAutomation()` | 默认 30 分钟一次，**在每个学生电脑上跑** |
| 新闻表 + 标签表 | `news_articles`、`news_tags`（`tag_type/tag_key/tag_role/confidence/method/evidence_span`） | 结构是齐的，学长说的「打 tags」有地方放 |
| 读新闻工具 | `search_news` / `read_news`（`tools/read-tools.ts:316/361`） | **只查本地库**，`limit: 500` 全表拉出来再用关键词过滤 |
| 实时抓取 | `news-lab.ts:241/291` → `crawlAndIngest` / `searchAndIngest`（DeepSeek Search API + 抓网页正文） | 这条是慢的根源，一次 60–200 秒 |

**三个真问题**：

1. **打标签没在入库时做**。`news_tags` 由离线管线 `pipeline/tag-content.ts` 填，
   客户端定时刷新只入库不分类 → 工具拿不到标签，只能全表关键词匹配。
2. **检索是「拉 500 条再过滤」**，没有按时间/相关性排序，命中质量差，于是模型转去实时搜。
3. **实时搜在请求路径上**。学生一问，模型调 `search_news` 发现库里没有 → 走
   `searchAndIngest`（联网+抓正文）→ 这一轮就卡在那里，而且**没有超时**。

## 二、目标形态（学长口径）

```
服务端：定时爬 → 清洗 → 打 tags（复用离线管线）→ 入库（带发布时间、来源、正文）
客户端：AI 调工具 → 工具按 tags + 时间 + 相关性检索 → 返回候选 → 读正文 → 回答
```

关键是**把「抓」和「答」解耦**：抓在服务端异步做，答的时候只做本地检索。
这也符合 `single-agent.md`：工具负责取材料，判断留给模型；不预取、不自己塞。

## 三、分三步做（先做 1，不动架构）

### 第 1 步：客户端先把「慢」掐掉（0.5–1 天）

| 改动 | 说明 |
|---|---|
| `search_news` 改为「本地检索优先 + 明确告知库外」 | 命中不足时返回「本地库没有这条，可联网补抓（约 1–3 分钟）」并**不自动联网**；由学生决定 |
| 检索排序 | tags 命中数 → 发布时间（近 30 天加权）→ 相关性（标题/摘要词频） |
| 结果带上 tags 与时间 | 模型能判断「是不是最近」「是不是同一概念」 |
| 实时抓取加超时 + 可取消 | 现在没有超时（F01/F02），至少 20 秒放弃并给一句人话 |

验收：问一条**库里已有**的新闻 → 1 次工具调用、<2 秒；问库里没有的 → 明确提示，不再静默等 2 分钟。

### 第 2 步：把刷新搬到服务端（3–5 天，需要一台服务器）

| 事项 | 说明 |
|---|---|
| 定时任务 | cron 每 30–60 分钟跑 `NewsService.refresh()` + `pipeline/tag-content.ts` |
| 增量入库 | 按 `news_articles_by_url` 唯一索引去重，只处理新增 |
| 打 tag | 用现有 `news_tags` 结构与既有标注规范（`docs/营销课程碎片化知识体系-设计与标注规范`） |
| 分发 | 两种都行：① 定期导出 `learning.db` 的新闻表打进安装包；② 客户端启动时拉增量（一个 `/news?since=` 接口） |

验收：新装机器**不爬也能查最近一周新闻**；客户端不再需要联网抓取。

### 第 3 步：检索质量（1–2 天，可延后）

- 关键词之外加「知识点 tag → 新闻 tag」的一跳匹配（学生问 ch04 概念时优先本章 tag 的新闻）；
- 备选：`sqlite-vec` 做向量检索（本地、免服务端），但先看 tags 够不够用；
- 不要在客户端做 embedding 模型下载（体积与首启时间都受不了）。

## 四、不做什么（避免重复走弯路）

- **不抄**重型方案：Elasticsearch / Milvus / 自建爬虫集群。这个产品是桌面端 + 小规模班级，
  SQLite + tags 排序足够；真到几千人再换。
- **不在请求路径里爬网页**（第 1 步就把这条掐掉）。
- **不把新闻正文塞进 system**（原则禁止预取）；正文只能经工具返回并留引用。
- **不让模型自己判断「要不要联网」**当作默认行为：默认查库，联网是显式请求。

## 五、风险

| 风险 | 说明 | 应对 |
|---|---|---|
| 版权 | 抓正文可能超出合理使用 | 只存标题+摘要+链接；正文按需抓、标注来源（`rights` 字段已有） |
| 源站结构变化 | 5 个源都可能改版 | 每个源单独 try/catch，失败不影响其它源；有 `ingest_runs` 记录可查 |
| 服务端成本 | 一台小机器足够（每小时几次抓取） | 可先用现有机器，跑通再谈 |
| 标签质量 | 打标靠模型，可能漂 | 保留 `confidence/method/evidence_span`，老师可复核（E 轮） |

## 六、与当前进度的关系

- 第 1 步可以立刻做，不依赖服务器，直接改善「涉及新闻就慢」；
- 第 2 步与「微信小程序」共用同一台服务器与同一套接口，建议一起规划（见 `track-0-delivery.md` 的手机端评估）。

## 七、第 1 步完成情况（`5267ca9`）

| 改动 | 结果 |
|---|---|
| `search_news` 默认只查本地库 | 没命中就如实说没有，并告诉模型「确实要最新可再调一次并 online=true」 |
| 联网改成显式开关 | `online: true` 才联网；有 45 秒上限（`withTimeout`） |
| 排序 | 关键词命中（标题 6 / 摘要 3 / 正文 1）> 新鲜度（7 天内 +3、30 天内 +1）> 时间倒序 |
| `news-lab` 实时检索 | 同样 45 秒上限，超时说「已放弃，不拿无关文章凑数」 |

**测试抓到的设计错**：新鲜度一开始是无条件加分，结果「今天发的无关新闻」会混进
搜索结果；现在只有命中关键词后才加新鲜度分（`scripts/verify-news-search.ts` 第 5 条守着）。

**另一个顺手修的 P0**：断网时学生会看到 `fetch failed`（英文栈）。
错误文案抽成 `apps/desktop/src/main/errors.ts` 纯函数并补全映射：
断网 / DNS / 连接重置 / 401 / 403 / 402 余额不足 / 429 / 超时 / 流中断 / 磁盘写满 / 模型空返回，
并区分「聊天」与「交卷」两种上下文（交卷会说「这次作答没有记成成绩」）。
`scripts/verify-errors.ts` 13 条断言，删掉任一映射就会变红。

## 八、下一步（第 2 步）

需要一台服务器 + 一个 HTTPS 域名。与手机端共用同一套接口，建议一起规划。
在服务器就位之前，第 1 步已经把「涉及新闻就卡两分钟」消掉了。
