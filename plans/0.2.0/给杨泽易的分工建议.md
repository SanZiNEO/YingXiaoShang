## 三、需要我们这边做的（你不用碰，避免互相踩）

| 事项 | 为什么不能并行 |
|---|---|
| **桌面端交付包**（electron-vite build → asar → zip → 冒烟） | 打包脚本与 asar 重打流程只有一套，改一次要全量验 |

| **`docs/requirements/` 的口径** | 需求文档是判据来源，多人改会打架 |

**如果你觉得某块应该改，别自己动手**：写一段说明发我，我来判断和安排。
这不是不信任，是我们已经踩过「两边同时改一处、互相覆盖」的坑。

## 四、流程：从「直接推 main」改成分支 + PR

现在你 9 个提交是直接推到 `main` 的。这有两个实际问题：

1. **我这边拉不下来**（网络原因），本地和远程已经分叉，容易互相覆盖
2. **没有第二双眼睛**：我们刚做过一次独立复核，抓出 1 个 P0 + 7 个 P1，
   其中一条是我自己写的正则违反设计原则——**我自己看自己的代码是看不出来的**

所以从现在开始：

```
feat/xxx 或 test/xxx 分支
  → 提 PR（标题写清做了什么、怎么验证的）
  → 我们做一次独立复核（会给你具体到行的意见）
  → 改到过 → 合并
```

**PR 描述请包含三样**：
1. 改了什么（一句话）
2. 怎么验证的（跑了什么命令、看到什么结果）
3. 有没有不确定的地方（这条最重要，我们最怕的是"看起来没问题"）

## 五、几条技术约定（省得返工）

1. **采集服务不写业务表**：只写 news 相关表（`news_articles`、`ingest_runs` 等）。
   学情、题目、会话那些表由应用侧写，两边同时写同一个 SQLite 会偶发锁冲突。
2. **正文门槛**：本地检索现在放宽到 40 字，但必须带 `content_status`（full/partial）。
   40 字的片段只能当线索，不能让模型当材料讲。
3. **抓取失败不阻塞**：单源失败记 `partial`，不要整轮 fail。
4. **不引入需要编译的依赖**：Playwright 只作为可选 extra，默认不装。
5. **密钥不进仓库**：`.env.local`、`.venv`、`.artifacts` 都已在 gitignore 里，别破例。
