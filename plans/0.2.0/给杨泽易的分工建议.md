### ② 新闻正文质量抽检（这是你 50 个源最该做的一件事）

**为什么**：50 个源里一定有一批抓回来的是导航栏、登录墙、Cookie 提示、或者「正文 == 摘要」。
这些条目进了库，模型就会拿它们当材料讲，学生看到的就是胡话。**源的数量不重要，能用才重要。**

**交付物**：`services/news-crawler-py/scripts/quality_report.py`

要输出一份 markdown 报告，按源统计：
- 正文长度分布（P10/P50/P90）
- 「正文 ≈ 摘要」的比例
- 疑似非正文的比例（含「登录」「注册」「Cookie」「版权所有」「扫码」等导航特征）
- 重复率（同一 `content_hash` 出现多次）
- 空标题/空日期比例
- 每源给 3 条**最差样本**（原文截断 200 字），便于人工判断

最后给结论：**建议保留 / 建议降级为「只取标题摘要」 / 建议下线** 的源清单。

**验收**：在现有库上跑一遍，产出一份真实报告，并明确指出最差的 5 个源 + 证据。
（如果库是空的，先 `news-crawler refresh --wait` 跑一轮再统计。）

**可以直接粘给你的 AI**：

```
在 services/news-crawler-py 里新增 scripts/quality_report.py：
- 直接读 NEWS_CRAWLER_DB 指向的 sqlite（复用 src/news_crawler/db.py 的连接与表结构）
- 按 source 分组统计正文长度分位、正文≈摘要比例、导航词命中率、content_hash 重复、空字段比例
- 每源输出 3 条最差样本（截断 200 字）
- 生成 markdown 报告到 ../../plans/0.2.0/news-source-quality.md
- 不要修改任何已有模块，只新增脚本
```

### ③ 采集服务 Docker 化

**为什么**：桌面包（`electron-builder.yml`）只打包 `out/**`、`templates/**`、种子库和提示词，
**永远不会带 `services/` 和 `.venv`**。所以你的采集服务的正式形态就是「服务器上的一个容器」。

**交付物**：
- `services/news-crawler-py/Dockerfile`（`python:3.12-slim`，只装 `httpx / beautifulsoup4 / lxml`，**不含 Playwright**）
- `docker-compose.yml`：服务 + 数据卷（DB 目录挂载）+ 健康检查
- cron 示例：每 30 分钟 `refresh`
- 环境变量说明：`NEWS_CRAWLER_DB`、`NEWS_CRAWLER_PORT`、`NEWS_CRAWLER_WORKERS`

**验收标准**：
1. `docker compose up -d` 后 `GET /health` 返回 ok
2. `POST /run` 能入库新文章（`/stats` 有变化）
3. `docker compose restart` 后数据还在（卷挂对了）
4. 镜像大小 < 400MB

**注意**：服务端部署时采集服务与应用**共用一个 DB 文件是可以的**（两边都 WAL + busy_timeout=5000），
但你要保证采集只写 news 相关表（`news_articles`、`source_runs`、`news_tags`），不要碰学情/题目/会话表。

## 二、第二批

### ④ SQLite → PostgreSQL 迁移工具

**为什么**：一个人用 SQLite 没问题；40 人同时用，写锁会打架。M1 上线前必须换 Postgres。

**交付物**：`tools/migrate-pg/`
- 读 `learning.db` → 建 PG schema（类型映射：TEXT/INTEGER/REAL/JSON 存成 jsonb/text）
- 数据导入（批量 COPY 或 executemany）
- **幂等**：重复跑不重复插入
- **双跑校验**：迁移后逐表比对行数 + 抽样内容 hash，不一致就报错退出
- 一份 `README`：怎么在新库上跑、怎么回滚

**验收**：
1. 在 `seed/learning.db` 上跑，逐表行数一致
2. 故意手改 PG 里一行，校验脚本能报「不一致」
3. 跑两遍不报错、行数不变

**不许碰**：不要改现有 `packages/db` 的 schema 定义，只写迁移工具。

## 八、你的打标建议：采纳了，但范围要收窄

你说「入库其实可以不用 LLM 打标签 / 人工先给知识点打 tag / 用分类器分」——**这个判断是对的**：

- 知识点是**封闭集合**（228 个 kp / 13 章），本质是分类问题，不是生成问题
- LLM 打标三个硬伤：每篇一次调用（成本随文章数涨）、同一篇两次结果不同（不可复现）、判错无法审计
- 人工打一次 + 分类器批量跑：可复现、可回滚、便宜

**但要收窄**：先做**章节级（13 类）**，不要一步到位做 228 个知识点。
13 类标注成本极低、准确率高；228 类会把项目拖死。

**要交付什么**：
1. 一个导出待标池的脚本（按时间/来源筛，去重）
2. 一个 CSV 或轻量界面：`id, title, summary, 章节标签`
3. 分类器：TF-IDF + 线性模型或朴素贝叶斯即可，**必须给可解释依据**（命中词/相似度），
   因为老师会问「为什么这篇算第 7 章」
4. 一个评估脚本：人工标 100 条做 golden set，报告准确率与混淆矩阵

## 十、一句实话

你大一开始能搭出这个量级的基建，学得很快。我们最需要的不是「什么都做」，
而是**把一件事做到能验收**：一条真能变红的用例，比 30 个漂亮的空文件有用得多。

有不确认的地方直接问，别猜。我们这边的原则是：
**宁可你说「这块我不会」，也不要交一个「看起来跑通了」的东西。**
