# 现象排查：问得大就慢、连续发问会卡（2026-11-05）

> 依据：本机 `~/.learning-agent/data/learning.db` 的真实数据 + 代码定位。
> 复测命令：`python tools/turn-duration.py`

## 一、实测数据（23 个真实轮次）

| 指标 | 值 |
|---|---|
| 中位耗时 | **2.3 秒** |
| 最快 | 1.3 秒 |
| 最慢 | **204.8 秒** |
| 超过 60 秒的轮次 | 4 个（204.8s / 155.6s / 135.5s / 121.0s） |

**关键反例**：463 字和 1151 字的长问题，耗时只有 **2.1 秒 / 2.0 秒**。

**所以「问得长」本身不是慢的原因。** 慢的轮次和问题长度没有相关性，
相关性在另一个变量上：**这一轮有没有去查资料（走工具循环）**。

## 二、慢的机制（代码事实）

一轮对话里，模型每要一次资料，就要多一次完整往返：

```
第 1 次模型调用 → 模型说「我要 read_kp」
   ↓ 执行工具
第 2 次模型调用 → 模型说「我还想看新闻」
   ↓ 执行工具
第 3 次模型调用 → 这次才写正文
```

代码里 `team.ts:210` 原先写死 `maxRounds: 10`，加上收口轮最多 **11 次模型调用**。
单次 10–20 秒（含 `thinking` 推理），10 轮就是 100–200 秒 —— **和实测的 120–205 秒完全吻合**。

另外三条加重因素：

1. **工具轮次期间不吐字**。提示词要求「正文只在不再调用工具的那一轮写」
   （`team.ts` 的 system 拼装处），所以查资料的几十秒里界面上什么都没有，
   观感就是「它在发呆」。
2. **工具是串行的**，一次只查一个，每查一个都要一次往返。
3. **没有超时、没有取消**（审计 F01/F02）。慢的时候只能等，也没有「停止」按钮。

## 三、「连续发问会卡」的机制

渲染层其实**有排队**（`App.tsx:897-960` 的 `busyRef` / `queueRef`），
第二次发送不会并发，而是进队列，界面上显示「排队 N」。

所以「卡住」不是死锁，是**串行放大**：

```
第 1 问：120 秒
第 2 问（排队）：轮到时再 120 秒
第 3 问（排队）：再 120 秒
```

三连问 = 6 分钟没有反馈。而且排队期间界面只有一个「排队 3」，看不到任何进度。

**已排除的怀疑**（都查过，不是原因）：

| 怀疑 | 结论 |
|---|---|
| 两个请求并发打同一个模型 | 否，渲染层串行 |
| SQLite 锁死 | 否，`busy_timeout=5000`，且 turns 表 23 条全是 `completed`，没有残留 running |
| 会话历史越滚越大拖慢 | 否，最长会话只有 11 条 / 2813 字 |
| 数据库里卡了半截的 turn | 否，0 条异常 status |

## 四、顺带查出来的一个真 bug（影响学情，不影响聊天）

23 个 turn 的 `record_json` 全是 **2 字节 `{}`**（`index.ts:495-507`）。
记录器的 `asRecord()` 要求 `turnId` + `status` 字段，拿到 `{}` 直接 `break`
（`recorder.ts:25-30`、`:139`）。

**后果**：水位永远不推进，学情/成长记忆从不更新 —— 这就是审计里的 **F11**，
现在有了真实数据佐证：不是「可能有问题」，是「23 轮全部没有记录」。

## 五、现在能做什么（不重新打包）

| 做法 | 效果 |
|---|---|
| **一次只问一个具体问题**，等回答完再发下一句 | 避免排队叠加 |
| 问「是什么 / 区别 / 为什么」这类概念题 | 通常 2 秒级（不查资料） |
| 问案例、新闻、出题 | 必然走工具，预期 1–3 分钟，别当成卡死 |
| 连续问时看左上角「排队 N」 | 有数字=在排队，不是死机 |
| 真的很久没动 | 关掉软件重开（没有停止按钮，这是已知缺陷） |

## 六、代码上要修什么（对应轮次）

| 问题 | 修法 | 轮次 |
|---|---|---|
| 最多 11 次模型调用 | 删掉 `maxRounds` 与强制收口，让模型自然结束（审计 F03） | B 轮 |
| 工具串行 | 声明并行安全后由原生调度并行（审计 §4.3 并发分类） | C/D 轮 |
| 查资料期间不吐字 | 允许短进度说明；界面显示真实阶段（F04/F05） | D 轮 |
| 无超时/无取消 | 接原生取消链与 provider 空闲超时（F01/F02） | B/D 轮 |
| `record_json: {}` | 聊天也写完整 TurnRecord（F11） | C 轮 |
| 排队无进度 | 排队项显示「第 N 个，预计 X」 | D 轮 |

## 七、一句话结论

**不是「问得大就慢」，是「查资料就慢」。** 查一次 = 一次完整模型往返，
而这个版本最多允许 11 次往返且全程不吐字、不能停。
连续发问之所以「卡」，是排队把每次的超长耗时串起来，界面又没有进度。

这四条都在 B/D 轮的修复清单里，不是玄学。

## 八、「同一会话连续 4 轮左右卡住」（用户 2026-11-05 补充的现象）

**先纠正上一节的推断**：不是「上一条没答完就发下一条」的排队问题。
实际情况是**每轮都等回答完再追问，问到第 3–4 轮时，下一问卡住**。

已排除（都查过）：

| 怀疑 | 证据 |
|---|---|
| 渲染层并发 | 有 `busyRef`/`queueRef`，串行 |
| SQLite 锁 | `busy_timeout=5000`；`turns` 表 23 条全 `completed`，无残留 running |
| 历史累积拖慢 | 最长会话 11 条 / 2813 字，量级太小 |
| 模块级状态泄漏 | 无模块级 Map/Set；`inFlightSubmissions` 在 finally 里删 |

**目前最可能的解释是模型 API 限流**，理由：

1. 单轮最多 11 次模型调用（`maxRounds=10` + 收口轮）；
2. 4 轮 = 20–40 次请求，集中在几分钟内，正中常见的每分钟请求数限制；
3. 代码里**没有 429 处理、没有退避重试**，`finish` 又不区分失败类型（审计 F02），
   所以触发限流后不会报错，只会一直等。

**怎么确认（需要现场证据）**：

- 用包里的 `调试启动.bat`（`ELECTRON_ENABLE_LOGGING=1` + `--enable-logging`）复现；
  卡住时看窗口最后二三十行，重点找 `429`、`rate`、`timeout`、`abort`。
- 同时跑 `python tools/turn-duration.py`，看卡住那一轮在 `turns` 表里
  是「有记录但很慢」还是「根本没有记录」：
  前者是慢，后者是请求没发出去/没返回。

**如果确认是限流，修法**（B/D 轮）：

- provider 侧处理 429：读 `Retry-After`，指数退避重试，并把「正在重试」显示到界面；
- 界面给出可区分的错误文案（限流 / 网络 / 超时），不能一律「转圈」；
- 减少无谓请求：删 `maxRounds` 与强制收口（F03），工具并行（C/D 轮）。

## 九、后续实测补记（2026-11-07）

### 「越聊越慢」的会话内曲线（本机 DB）

| 会话 | 逐轮耗时 |
|---|---|
| `chat_mw5xw4fo_d9rrhy` | 2.8 → 2.8 → **61.3** → **76.4** |
| `chat_mvfao3ns_w1g7v6` | 3.0 → **43.0** → **204.8** |
| `chat_mw3kmnsx_1ia8y5` | 2.3 → 2.3 → 1.8 → **121.0** |

三个因素相乘：历史全量重放（输入变长）→ 单次变慢 → 上下文变多后模型更想多读
→ 轮数上升 → 更慢。

### 已排除的两个外部猜测（都有实测）

| 猜测 | 实验 | 结果 |
|---|---|---|
| 模型 API 限流 | 连打 20 次 Messages 端点 | 全 200，最长 1.19s |
| 限流（真实负载） | 带工具 + 长 system 的 `/chat/completions` 连打 40 次流式 | 全 200，无一次 >20s |
| 原生运行时循环有累积 | 同一会话连跑 8 轮原生 turn | 每轮 1–2s，全 completed |

所以慢的来源是**应用自己那一层**（老循环的轮次 + 历史重放），不是供应商。

### 已落地的第一处提速（`b100426`）

`read_kp` 支持 `names` 批量 + 提示词要求一次读齐：

| 场景 | 改前 | 改后（实测） |
|---|---|---|
| 1 个概念 | 2 次调用 | 2 次 / 4.0s |
| 3 个概念 + 关系 | 4 次 ≈20–30s | **2 次 / 7.2s** |
| 5 个概念对比 | 6 次 ≈30–40s | **2 次 / 6.7s** |
| 连续 6 轮 | 最慢 204.8s | **每轮 4.0–5.7s** |

### 还没做的提速项

1. 历史瘦身（只带最近 2–3 轮 + 摘要）——解决「越聊越慢」
2. 前缀缓存（system 固定、变化内容后置）
3. 首字可见 + 可取消（不省时间，但不用干等）
4. 删 `maxRounds` 与强制收口轮（B 轮）
