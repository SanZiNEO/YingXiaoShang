## D-1 产品定位：以老师方向为主，不追概念创新（2026-11-04）

**参与**：秋华、杨泽易、天才（三人讨论）

**结论**：主线仍是「答疑 + 成长佐证」，即老师给的原始方向。
天才提的「把应用做成记录 + 验证（笔记 + 做题）、AI 是每人量身定做的梯子」方向**不采纳为主线**，
理由：

- 那需要重新定义学习类产品形态，我们没有这一层经验；
- 一旦做成，验收标准要重写，MVP 无法按期交付；
- 老师的诉求很具体（问问题能问清楚、案例可回溯、成果能带走、成长有证据），没有要求产品创新。

**但吸收其中两条低成本部分**，见 D-4。

## D-2 前后端：未来走服务器，当前不拆进程（2026-11-04）

**依据**：杨泽易——「未来是要走服务器的，因为要对用户信息进行追踪」；
「dsh 正好是分开的，可以直接拉服务」。

**结论**：

- **长期**：agent 与数据在服务端，桌面/网页都只是客户端。
- **当前**：不拆成两个进程。理由是现在拆只会让调试更难，而 dsh 本身已经把
  「运行时 / 会话 / 存储 / 传输」分开了，将来换宿主不用重写业务。
- **现在要守住的一条**：**界面只通过一层事件/请求协议跟运行时说话**（现在就是
  `learning:chat` / `learning:chat-event`）。做到这一点，将来搬到服务器就是换传输，
  不是改业务。**反例**：在渲染层直接拼 prompt 或直接读库。

## D-3 不自己搓 agent 循环（2026-11-04，杨泽易）

原话：

> 不要自己搓 agent 循环，有什么就往上下文、skill、技能里面塞就行了，直接用现成循环。
> 就是用人家循环，然后把我们要的功能变成 skill、工具、上下文之类的。
> 比如你现在就要对学生进行成长评价，你就要让 ai 能用工具去查看学生的每期评价。

**落成**：这就是 0.2.0 的 A–F 轮。判断「这个功能该放哪」的顺序固定为：

1. 能做成交互规则、不需要模型判断的 → **工具**（如查学生每期评价）
2. 是「怎么算好」的判据 → **skill**
3. 是「我是谁、什么时候该问、什么时候该给」 → **提示词 / 上下文**
4. 以上都不是，才考虑动循环——而这一条现在等于禁止。

## D-4 采纳天才的两条（低成本、不改主线）（2026-11-04）

| 天才的意见 | 采纳方式 | 为什么便宜 |
|---|---|---|
| 「本质是记录 + 验证（笔记 + 做题）」 | 成长卡按**章节时间点**取数（第 N 章学完之后），再与前一章对比。已有题库与作答记录，缺的只是这条取数线与判据 | 不动产品形态，等于把 R13/R14 做实 |
| 「AI 是每人量身定做的梯子」＝最近发展区（ZPD） | 做成 `growth` skill 里的**判据**：题目难度落在「会一点但还会错」的区间；连续答对就抬难度，连续错就退回上一档 | 参考实现存在（见 D-5），且是判据不是代码 |

**不采纳**：「任务目标不由 AI 管、学生自己定目标」——老师会布置要求，学生自行探索在
课堂场景里没有落点；且当前实现里 AI 本来也不管任务目标，这条等于确认现状。

## D-5 参考项目 OpenMAIC：能抄什么、不能抄什么（2026-11-04）

`THU-MAIC/OpenMAIC`，42.7k star，MIT，TypeScript/Next.js，
「一键生成沉浸式多智能体互动课堂」，有 JCST 论文。

**能抄**：

- `eval/zone-of-proximal-development`——**最近发展区**（ZPD）的现成实现思路，正好对应 D-4 的「梯子」
- 「记录 + 验证」的产品结构：他们的 `eval/` 按能力分目录，每条有可判定的观察点
- `skills/` 的组织方式（`agent-runtime`、`openmaic` 分包）

**不能抄**：

- **多智能体编排**。我们是单一说话人（R01），抄过来就破了原则。
- **Next.js + Docker + 渲染服务**那套重架构。我们是桌面端，不需要。
- 它的完整能力面（白板、课件生成、多人课堂）。那会把 MVP 拖成另一个产品。

**结论**：当**判据与产品结构的参照**，不当架构参照。

## D-6 先做出来，再优化（2026-11-04，杨泽易）

> 你真的做完了才能感觉自己设计是否合理。光想的话是做不完的。
> 就怕搞半天方向错了全部得砍 → 这种损失也小，总比一直计划空想好。

**落成**：A/B 两轮**不许无限期调研**。A 轮核实完就进 B 轮跑通；
功能不好再优化，新想法再加，不要的直接砍。**禁止在计划阶段追求完美设计。**

## D-7 对话摘要放 system，不算「塞业务材料」（2026-11-07，裁决：留；复核提出的疑点）

**疑点**：`single-agent.md` §3 说「system 里只放稳定指令 + 运行时事实 + 目录」，
历史压缩的摘要每轮都出现在 system，是不是违规？

**判据（逐条对照原则原文）**：

1. §3 明确把**运行时事实**列为 system 的合法内容；「这段会话里发生过什么」属于运行时事实。
2. §3 禁止的是**枚举项**：正文、原文、新闻全文、题库、历史产物正文；也不许代码替模型
   挑知识点、拼原文塞进 system。摘要里没有这些，压缩的是学生自己说过的话和程序阶段记录。
3. §3 第 52 行的「每轮都出现的内容要么稳定、要么目录，否则应变成工具」针对的是
   **重复预取的固定材料**；摘要是每轮变化的，做成工具（`read_history`）只会多一次往返，
   而且违反 §4「工具不持有本轮状态」。
4. 摘要标题写明「程序压缩，不是学生原话」，不冒充学生发言，也不声称「已读」。

**替代方案与被否的原因**：把摘要挪进 messages 当第一条，就必须给它安一个说话人，
违反 §1「只有一个说话人」的风险更大。

**约束（越界即算违规）**：
- 摘要里出现教材正文、新闻全文、题库、产物正文 → 违规；
- 摘要长度不设上限 → 违规（现在是 700 字）；
- 用摘要替代读工具（「摘要里有定义就不用 read_kp」）→ 违规，摘要不产生引用。

**退场条件**：D2（原生运行时 + 上下文管理落地）后，`packages/agent/src/history.ts`
由原生上下文压缩接管，本文件删除。届时删掉本决策的落地实现，保留决策记录。
